# ADR-0015: Derived-state snapshots for tool calls

Status: accepted (2026-10). Its future work on cold starts is taken up in ADR-0016.

## Context
ADR-0013 made every tool call rebuild its campaign from disk, so a call could never hold state the record lacks. That rule is right, but the implementation priced it at the whole log: each call re-read and re-parsed `events.jsonl`, re-folded it (state, budget, driver history), scanned the request journal, and then re-serialized and fsynced the entire log to commit. Profiling `reserve_evaluation` + `settle_evaluation` on a file-backed workspace at 2000 queries put the time in JSON decoding of events (`EventLog.from_jsonl`), JSON encoding (`EventLog.to_jsonl`), `reduce` and `Cost` arithmetic, and `journal_lookup`: all linear in log length. Measured latency grew from about 7 ms per call at the start of a campaign to about 187 ms at 5000 queries, which makes the agent surface the bottleneck of the campaigns it exists to serve.
## Decision
The event log remains the only source of truth (ADR-0004). Everything else is a derived cache that is validated against the log before every use and rebuilt from it when validation fails.

* **Commit is an append.** New events are written to the end of `events.jsonl` in one fsynced write; a new campaign's log is created atomically. A line is committed when its newline is on disk, so an unterminated final fragment is a torn append: readers ignore it and the next writer, holding the lock, truncates it. A corrupt complete line is still an error.
* **Sessions.** A tool call works on a `Session`: the live campaign plus an incremental fold (`StateFold`, whose final state is `reduce` by construction), and lookup tables for reservations, closings and request ids, all brought forward over only the events appended since. After a call, the session is kept by the `CampaignStore` and offered to the next call in the same process.
* **Validation.** A kept session records the byte offset it accounts for and the raw bytes of its last event. Before reuse, the log must be at least that long and carry exactly those bytes at that position; events appended since (by this or any other process) are read from the offset, applied to the campaign (history, budget, driver) and folded in, and the rng streams are restored from `checkpoint.json` whenever the log or that file moved. Sessions with uncommitted changes (an error after a partial mutation) are dropped, not reused. Any failure falls back to a full replay.
* **Snapshot file.** `snapshot.json` (`cadaques.snapshot/1`) stores the fold, the number of events, the byte offset, the SHA-256 of the last event and of `spec.json`. It is rewritten (atomically, without fsync) after each commit and serves cold read-only calls, `get_campaign_status` and `list_campaigns`, without parsing the log: it is validated like a session, folded forward over any newer events, and ignored if anything disagrees. Mutating calls never trust it; they replay the log or use a validated session. *(Amended by ADR-0016: in release 0.4.1 the snapshot is schema 2, and a new process whose campaign has a driver without history starts its mutating session from it, after the same validation plus a checksum of the fold.)*
* **Journal index.** The request journal is indexed by byte span, incrementally and with the same offset-and-last-line validation, instead of re-parsed per call.

Rejected alternatives: keeping the full-rewrite commit and caching only reads (the rewrite alone is linear and its fsync grows with the log); a database or index file as a second record (violates ADR-0004 and ADR-0008); trusting a cache on file mtime (does not survive copies, restores or edits).
## Consequences
Per-call latency is independent of log length for a long-lived process (a Python `Toolbox`, the MCP server): measured flat at about 0.7 ms per call from 100 to 5000 queries. A cold process (each `cadaques-agent call`) answers status and listings in time independent of log length, but its first mutating call still replays the log once, because driver history is rebuilt from events; ADR-0016 removes that cost for campaigns whose driver keeps no history by persisting the snapshot as a starting point for a new process; for learning drivers it remains, and making it constant needs a driver-state protocol. Validation covers the log's tail, not its interior: an edit in the middle of an append-only file by an outside actor is detected by a cold start, not by a running session, and `replay` from the file is the audit. Torn appends can in principle split a multi-event call between its events, leaving a shorter but self-consistent record; every prefix of the log is a valid campaign state, and the request journal and `request_id`-based reconstruction (ADR-0013) cover the retry. *(Amended by ADR-0016: in release 0.4.1 such a call is not committed at all; see there.)* `Session` and `StateFold` are internal; the tool schemas and the on-disk event schema (`cadaques.events/2`) are unchanged, and a workspace written by 0.4.0 is read as is.
