# ADR-0016: The persisted snapshot starts a new process

Status: accepted (2026-10). Completes the future work named in ADR-0015.

## Context
ADR-0015 made a long-lived process (a Python `Toolbox`, the MCP server) independent of log length, and let a cold process answer status and listings from `snapshot.json`. It left one cost linear in the log: the first mutating call of every new process (each `cadaques-agent call`) still replayed the whole log, because the session needs the campaign's driver history and the lookup tables for reservations, closings and request ids, all of which were rebuilt from events. Measured on the ADR-0015 branch, a reserve and settle in a fresh process (an external-driver campaign) took about 8 ms at 20 queries, 41 ms at 1000 and 198 ms at 5000, and the command line is exactly the pattern that pays that on every call.

The replay is only needed for what it rebuilds. For a campaign whose driver keeps no history (`ExternalDriver`: the operator proposes every point and `observe` is a no-op, which is the agent-operated case ADR-0013 exists for) the history is never read, and the three lookup tables can be answered from a small index plus, rarely, the log itself.

## Decision
The event log remains the only source of truth (ADR-0004). A new process starts from two caches, each validated against the log before it is believed, and falls back to the full replay on any doubt.

* **`snapshot.json`, schema 2.** As in ADR-0015 (fold, number of events, byte offset and SHA-256 of the last event covered, SHA-256 of `spec.json`), plus a SHA-256 of the fold itself, so that a snapshot that was edited or damaged without recomputing its checksum is rejected. It is still rewritten atomically after every commit. Schema-1 snapshots are ignored and replaced.
* **`events.index.json`, schema 1.** `request_id` to the byte span of that request's events in `events.jsonl`, with the same offset and last-event digest. It is linear in the number of requests, so it is not rewritten on every commit: a process's first commit rewrites it when it lags the log by 64 events or more (the one-call-per-process pattern therefore bounds what the next process must scan), and a long-lived process lets it lag by 1024. Both files are written atomically without fsync; losing either costs one replay.
* **The start.** If the snapshot and the index both prove themselves against the log and the campaign's driver is `ExternalDriver`, the session is built from the spec, the budget is charged with the snapshot's total, the events after the index are read (a bounded number: those after the index, which include those after the snapshot), those after the snapshot are applied and folded in, and the rng streams are restored from `checkpoint.json`. The session's `EventLog` holds only that tail; its `base` is the number of earlier events, so sequence numbers and `len()` continue the record. Anything else (another driver, a missing or mismatched file, an index newer than the snapshot, a span that does not end where the snapshot says) replays the log, and the next commit rewrites both caches.
* **The unread prefix is looked up, not assumed.** A retried `request_id` reads its events through the index. An evaluation that is not open in the snapshot (unknown, or closed before it) triggers one scan of the log to fill the reservation and closing tables, so `already_settled` still reports who settled it and when. `get_events` reads the file.
* **The journal is not scanned on the common path.** Every journal entry belongs to a call that committed events carrying its `request_id`, so a `request_id` the record has never seen cannot be in the journal. `_mutate` consults the record first and reads the journal only for a retry. Together with the torn-tail repair of 0.4.1, `journal_append` reads only the last byte of the journal.

* **A call is committed all or nothing.** The append of a multi-event call (a reservation is a `driver_proposal` and an `evaluation_reserved`; a run is many) can reach the disk in part after a power loss, which ADR-0015 accepted as a shorter but self-consistent record. That leaves the retry unable to tell a half-applied call from a finished one, and a refusal that stopped midway looks like a different refusal. The first event of every call that appends more than one carries `call_events`, the number it wrote. A reader that finds the log ending inside such a call (fewer events than declared, with or without a torn line after them) treats the whole call as uncommitted: `read_events_from` leaves it unread, so every offset the caches record is a call boundary, and the next writer truncates it away under the lock. Logs written without the stamp read as before.

Rejected alternatives: serializing driver state into the snapshot (every driver would need a state protocol, and the replay is what keeps drivers honest about being functions of their history); a hash index file with random access (more machinery than a bounded forward scan needs at the sizes agent campaigns reach); trusting the snapshot for mutating calls without a checksum of the fold (the digest of the last event proves the position, not the content).

## Consequences
The first mutating call of a new process no longer depends on the length of the log for an external-driver campaign, apart from loading the request index, which is linear in the number of requests but a small constant (a few bytes of JSON per request against a few hundred per event): measured on the same campaigns, the fresh-process round trip is about 7.7 ms at 20 queries, 8.4 ms at 1000 and 11.8 ms at 5000 (versus 41 and 198 ms), the growth being the load of the request index; the first call after a long-lived writer, which finds the index up to 1024 events stale, costs about 15 and 18 ms at 1000 and 5000 and refreshes it. The warm latency of a long-lived process is unchanged, about 1.2 ms on that machine at every length. Campaigns with a learning driver (`AnnealedLocalDriver`, `BayesianDriver`) still replay once per process, because their knowledge is rebuilt from history; making that constant needs a driver-state protocol and is future work.

The checksum guards against corruption and edits that did not recompute it, not against an actor who can rewrite the workspace: such an actor can edit the log itself, and `replay` from `events.jsonl` remains the audit. Validation still covers the log's tail, not its interior (ADR-0015). Nothing on disk that 0.4.0 or the ADR-0015 branch wrote becomes unreadable: their snapshots are ignored, their workspaces are replayed once and upgraded by the next commit. The tool schemas and the event schema are unchanged.
